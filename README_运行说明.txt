设备维护台账数据分析网页系统
抽签序号：26（根目录exam_id.txt统一配置）

一、验收依据
按 references 中的《样例数据说明.md》《第47届技术比武AI应用实操考试实施方案.docx》《第四十七届技术比武AI技术应用考试要求.docx》实现，详见需求对照_26.md。
原始文件始终保留。新版按材料的逻辑异常剔除建议输出清洗维修CSV，并保存完整剔除记录。

二、Windows运行
1. 下载并完整解压到可写目录，推荐Python 3.12 64位；安装时勾选Add Python to PATH。
2. 确认exam_id.txt为26；双击run.bat，首次安装依赖需要网络。
3. 浏览器访问 http://127.0.0.1:8765。安装依赖后可以断网运行。
4. 管理员：admin / Admin@123456；普通用户：user / User@123456。
5. 左侧菜单包括设备台账、生命周期、运维综合分析、各设备维保频次、清洗报告；管理员另有账号管理。
6. 退出登录清除会话；关闭服务在控制台按Ctrl+C。程序只监听127.0.0.1，无debug/reloader。

准确的CMD命令（项目根目录）：
  py -3.12 -m venv .venv
  .venv\Scripts\python.exe -m pip install -r requirements.txt
  .venv\Scripts\python.exe app.py
只准备数据和图表：
  .venv\Scripts\python.exe app.py --prepare
自动验收并保存带抽签号日志：
  .venv\Scripts\python.exe verify.py
运行实际HTTP冒烟（先启动服务）：
  .venv\Scripts\python.exe smoke_http.py

三、Windows打包与交付
  build.bat
会安装requirements-build.txt、运行unittest、生成数据、用PyInstaller --onefile打包，再实际运行最终EXE的--prepare。失败返回非零状态。
成功后自动打开delivery\26，正式程序为delivery\26\26.exe，压缩包为delivery\26.zip。
不要误选build\artifacts构建中间产物。更新源码必须重新打包，旧EXE不会自动更新。
备用目录模式：
  build.bat onedir
目录模式需保留_internal等全部文件。正式验收前必须停止原Python服务，避免误把Python服务当作EXE。
当前云端为Linux，没有Windows运行能力；Windows构建、双击和浏览器验收需本机执行。

新版EXE内置打包时的exam_id.txt和两份原始CSV；仅复制EXE到空的可写目录时会自动创建缺失文件。
已有配置、原始输入和账号不会被启动初始化覆盖。模板/字体/默认输入从sys._MEIPASS只读加载，数据库、CSV、图表均写在EXE旁。
正式交付推荐完整26目录或26.zip，包含说明、清洗输出和审计证据。

新交付目录结构：

若复用旧delivery目录，旧辅助文件不会自动删除；新版ZIP仅保留顶层两份指定CSV，其他统计文件位于output。

四、具体清洗口径
1. 设备编号去除首尾空格后关联；台账5条、维修5条。斜杠日期规范化为YYYY-MM-DD（投用1条、报修10条）。
2. 维修人员缺75条填“未记录”；故障类型缺56条填“未分类”。缺金额2条、缺停机37条保留缺失，不填零。
3. 本地精确短语词典domain_rules.py识别3条现象/类型疑似冲突；保留原类型与规则证据，归入“未分类”待复核。
   未分类共59条；候选类型只是复核线索，未收录或含糊现象不武断推断，不按记录编号或固定数量标记。
4. 报修早于投用3条，其中2条还存在完成早于报修：从交付维修CSV剔除，共剔除3条而不是5条。
   全量维修追溯页面和“维修剔除记录”保留这些行；原始data CSV不修改。逻辑正确的零停机3条保留。
5. 维修编号不存在、关联歧义、重复维修单号、关键时间无效等检查也有实现，本批未发现对应额外记录。
6. 已报废缺报废日期1台，报废早于投用3台；设备仍在全量台账中，生命周期计算排除共4台。
7. 累计维修次数、停机时长、维修费用逐台核对原台账与原明细；对账同时保存原值、已知明细合计、缺失数和清洗后值。
   原始次数全部对应。原始停机：3台与完整明细不一致，37台因明细缺失不能完整核验。原始费用：37台不一致。
   清洗台账按保留的有效维修重新计算累计字段与最近维修日期；缺失停机的设备完整累计值留空，不通过原台账差额猜测缺失时长。
   未维修设备的累计零值是实际没有维修，而不是用零代替缺失。
8. 日期无法解析、负值或无效数值会标记并从受影响指标中排除。审计事件数可以重叠，不能直接当作独立异常行数。

五、业务统计
生命周期：已报废完整生命周期=报废日期-投用日期；在用已运行时长=固定截止日2026-09-22-投用日期；天数/365.25。
有效周期1076台，排除4台；相关分析将每台设备关联有效累计维修单数，包含无维修的0次设备，Pearson约0.7927107。
全量有效维修3758条，含4条晚于截止日的报修；截止日有效维修3754条另列，二者不能混用。原记录不因晚于截止日而删除。
故障分布主图用有效维修，表格另列原始类型计数。缺失及疑似矛盾归于未分类。月份停机按YYYY-MM聚合已知有效时长并显示缺失样本数。
各设备频次覆盖全部1080台，支持筛选和分页，图展示全局前20；不是按年故障率。车间、类别费用均值按有效费用样本数为分母。
维修方式按有效记录，报废原因按全部210台已报废设备（含周期不可算的4台）。类别故障与季节热力图都有相同来源的完整矩阵表。
季节图按跨年日历月份汇总，未校正各月份覆盖年数、在用设备暴露量，不据此作季节因果推断。

六、后端权限与账号持久化
每次业务请求先在before_request中从SQLite加载用户和角色；未登录重定向/login；普通用户GET/POST /admin均403。
视图另外有登录与管理员装饰器。前端隐藏菜单只是显示差异，伪造请求或session中自加role字段均不会授予权限。
账号位于runtime\accounts.sqlite3，密码采用scrypt哈希；初始化仅在账号表为空时创建默认账号，重启不清空或覆盖已有账号。
角色修改后下次请求立即按数据库生效，删除用户后原会话不能继续访问业务页。新增/退出表单有CSRF校验。
升级如需保留旧账号：先停止旧服务，将旧程序旁整个runtime文件夹复制到新程序旁，再启动。不要将个人账号库提交到GitHub。

八、离线和常见问题
本系统不依赖CDN、外部API或在线鉴权；安装好依赖后断网仍可运行。
可在相同Windows架构/Python版本的联网电脑准备wheelhouse：
  py -3.12 -m pip download -r requirements-build.txt -d wheelhouse
build.bat/run.bat检测到wheelhouse后使用--no-index安装。文件转移遵守现场规定；不要用Linux wheel给Windows安装。
找不到Python：安装Python3.12并勾选PATH后重新打开CMD。缺模块：用.venv\Scripts\python.exe -m pip install -r requirements.txt。
端口8765被占用：关闭旧服务再启动，不改为0.0.0.0。写文件失败：解压到当前用户可写目录。
旧EXE提示缺exam_id或data：优先启动delivery\26\26.exe，下载最新源码重新build.bat。
现场不要为验收重启考试机（机房可能重启还原）；停止/启动应用进程即可验证账号持久化。


新增：DeepSeek LLM 智能分析（可选联网，不影响离线必做功能）
1. 以 admin 登录，左侧打开“LLM 智能分析”。
2. 在管理员配置区粘贴 DeepSeek API Key 并保存。密钥只在本机 runtime/deepseek.key，不随源码和交付ZIP分发；重启保留。DEEPSEEK_API_KEY 环境变量优先。
3. 点击综合使用情况、生命周期与更新、故障与停机、费用与维保，或输入问题连续对话。可填设备编号（如 SB-0001）附加该设备摘要。
4. 点击后将统计摘要、问题、最近三轮对话发送到 DeepSeek，消耗API额度；不发送账号库、密码、维修人员姓名或整份原始CSV。模型仅解释与建议，不改台账、不算权限。
5. 普通用户也可提问，但后端禁止其 POST /ai/settings 配置密钥；未登录不能进入 /ai 或 POST /ai/analyze。
6. 网络、余额和密钥错误会在页面显示，离线统计仍可使用。前端按纯文本展示回答，不执行模型HTML或代码。
7. 云端因 api.deepseek.com 域名解析失败未取得真实模型回复，不能据此判断密钥有效性。需在Windows联网后实测；自动测试使用模拟响应，不冒充真实API成功。
